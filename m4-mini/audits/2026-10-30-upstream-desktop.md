# M4 Mac mini desktop: upstream audit, 2026-10-30

Scope: base M4 mini `apple,j773g`, built-in HDMI, existing Gravity stack, Omarchy desktop, and the owner's existing M-series research. Source review and the local object builds below are not native boot or graphics qualification. No target machine was accessed during this audit.

## Source heads and branch choice

- Omarchy Mac's default [`quattro`](https://github.com/omacom/omarchy-mac/tree/ba546a61f881c1fe9d79d75ec050eab048b8cb63) is `ba546a61`; the branch used as the draft PR base, [`quattro-upstream`](https://github.com/omacom/omarchy-mac/tree/a76179cdcf1e844251eecac2708b687c486aa497), is unchanged at `a76179cd`. They are different, diverged branches: GitHub's comparison reports 768 ahead and 859 behind. Do not describe the draft as based on the current default desktop. Reconcile its intended base and packaging/boot differences before integrating a desktop.
- The candidate kernel is [`6363990c`](https://github.com/techmore/linux-m1pro-touchid/tree/6363990c4a4535b36dccd6c9a972e124861274fa), based on [Gravity's `gravity-m4` head `4fc326f6`](https://github.com/GravityLinux/linux/tree/4fc326f6c25ccceb7515e2635c22e01fde5d3bac). The [Gravity package manifest](https://github.com/GravityLinux/packages/blob/711c2a110416d28010ccdd118b83111776bff207/sources.json) pins a different kernel (`dea38a96`), so the running `509` RPM is not reproduced or identified as an exact match.
- These are **two distinct Aurora repositories**. [Omacom's `integration/aurora`](https://github.com/omacom/linux-aurora/tree/aa64d8fa73ded0573a227662d295c4f2cb64a343) is 17 commits ahead of our baseline `0571e8d`; selected-file inspection still finds only the framebuffer power-domain keepalive in its J773g board file and no `DRM_ASAHI_M4` option. It does contain other 26.6 DCP work; this is not a claim it lacks all M4-related code.
- [Aurora Silicon's `integration/aurora`](https://github.com/aurora-silicon/linux/tree/23827fe87f4ffbabf5b7907a5907f9316286ce55) is a separate, newer tree. It has experimental `DRM_ASAHI_G16` for the qualified J713/T8132 GPU firmware, while its J773g board file still contains only the framebuffer keepalive. Its G16 work is not evidence that this mini's native HDMI or GPU works. GitHub reports 1,021 commits since an older M-series audit pin; the API comparison is capped/paginated, so selected files and commits here are not an exhaustive change audit.

## Priority findings

1. **Keep the complete HDMI/GPU boot contract together.** Gravity's J773g DT enables primary DCP HDMI-A with DPTX PHY 4, and the driver checks actual DCP firmware `26.6.2`; its G16 path checks `mBoot-18000.161.10` and reserved memory. [Gravity package sources](https://github.com/GravityLinux/packages/blob/711c2a110416d28010ccdd118b83111776bff207/sources.json) pin bootloader `f64760b5` and the M4 U-Boot patch series ending `a2f69136`. Firmware identity, loader memory fixups and the mini's installed versions remain unverified. Match those components before testing; do not assume source compilation proves handoff or HDMI.
2. **Early display is a bootloader issue too.** Gravity's RPM [applies `NO_DISPLAY`](https://github.com/GravityLinux/packages/blob/711c2a110416d28010ccdd118b83111776bff207/gravity-bootloader/m1n1-no-display.patch) to leave the framebuffer in place. A [later installer change](https://github.com/GravityLinux/installer/commit/486e81ba909b1db0be0acfb3993f8cbacfd79545) builds stage 1 with the same option and reports that T8132 DCP iBoot initialization otherwise crashes display firmware before Linux. Gravity's bootloader HEAD `f02d4a52` is 11 commits ahead of its packaged pin, including [stage-two memory handling](https://github.com/GravityLinux/bootloader/commit/093767c92525a621b71abbc373643493968eb7a0) and [framebuffer mapping](https://github.com/GravityLinux/bootloader/commit/3c5b96201bdafe75a752c4c8a848edd9b5208fc4); the latter reports a Neo result, not an M4 mini validation. Installer HEAD `64206232` is four commits ahead of its package pin, including [partition/firmware extraction fixes](https://github.com/GravityLinux/installer/commit/cba7296d130c0c8fdf58829e019fbd73e3851a26). Review these against a matched bundle; do not combine heads and call them the installed release.
3. **Mesa and compositor must match the kernel.** Gravity's pinned [Mesa `87ac51d4`](https://github.com/GravityLinux/mesa/tree/87ac51d411f0e58a9433567ec2666f457be89e1d) UAPI header is byte-identical to the candidate kernel header (SHA-256 `eb9f39e87dfe448dc044f54ab2d11b7493bf1359faca8fb76ece5f3583469015`). That is a useful interface check, not proof that the whole userspace stack or GPU works. Gravity packages `ASAHI_MESA_DEBUG=nocompress` for both sessions and the Plasma login service; no equivalent was found in the inspected Omarchy trees. Evaluate a J773g-scoped equivalent for both the actual greeter and user compositor, using the intended Mesa build. Test acceleration, scanout, hotplug, mode changes, recording and reboot; do not infer them from matching headers.
4. **The display handoff needs desktop integration.** The draft's `wait-for-display` waits for `/dev/dri/by-path/platform-soc:display-subsystem-card`; the current default `quattro` branch has a different [simpledrm handoff migration](https://github.com/omacom/omarchy-mac/blob/ba546a61f881c1fe9d79d75ec050eab048b8cb63/migrations/1784417043.sh), which waits for the Apple card and simple-framebuffer removal, with a fail-open timeout. Gravity's T8132 source defines `soc/display-subsystem`. Which helper actually runs on the intended install and whether the J773g produces that path must be verified; test a cold boot and HDMI hotplug rather than treating a disconnected monitor as a fault.
5. **The M-series scheduler/idle/Bluetooth work is not in the current kernel candidate.** The existing [R7 compatibility series](https://github.com/techmore/ElementaryOS_MSeries/tree/c6fd172c1abc1a31dbf9c70eef79c3bd7896cd8c/mseries/m4-mini/gravity/compatibility) adapts six scheduler/lifetime fixes, two M4 WFI/early-idle changes, and two BCM4388 Bluetooth initialization changes from Aurora Silicon. R6 built, but its WFI selection was too late for the boot CPU; R7's full kernel/package remains unqualified. The current candidate instead carries the two M-series kernel-repo patches 0066/0067 and four Gravity exports, not this series.
6. **Do not replay that series blindly over patch 0066.** A scratch replay of all ten patches on the candidate returned success with zero fuzz, but 0004/0005 use context-free insertions and placed the M4 job's `MODULE`, `RETAIN_JOB_ON_ENODEV` and `TimeoutData` members outside `impl sched::JobImpl for SubmissionJob` after 0066 shifted the file. Seventeen of the 18 recorded result files matched the earlier R7 replay; `g16_drm.rs` did not. Moving those members to the correct impl in a separate scratch checkout made the remaining `g16_drm.rs` delta match the 0066 notification-timeout changes; the corrected M4 GPU, idle, SMP and Bluetooth objects compiled locally. See [the machine-readable receipt](2026-10-30-upstream-desktop.json). This is not a production patch, full module link, KUnit rerun, unload test or native result.
7. **Ethernet and watchdog config are missing from this candidate.** Its resolved configuration has both `CONFIG_AQTION` and `CONFIG_TIGON3` disabled, and `CONFIG_APPLE_WATCHDOG=m`. The M-series target fragment enables the two NIC drivers as modules and makes the watchdog built-in. This is an actual configuration gap, but the mini's controller has not been enumerated in this audit. Aurora Silicon's [watchdog change](https://github.com/aurora-silicon/linux/commit/7f7ca4de90f53b0189cac0a1fa4debc692931622) describes early-boot timeout risk; enable and test the right options in a new candidate, including initramfs/root-device discovery and recovery.
8. **BCM4388 changes require the matching Wi-Fi implementation.** Aurora Silicon's [RX DMA change](https://github.com/aurora-silicon/linux/commit/3217ca6a52211e78b1f3fb84d19d9cf912f64294) reports fixing a DART fault on an M4 Pro and depends on an earlier packet-direction change. In this Gravity candidate, `brcmf_msgbuf_init_pktids()` accepts a direction but does not assign it; its zero-initialized field is `DMA_BIDIRECTIONAL`, including for RX and TX. Therefore the exact precondition of Aurora's fix is not present; compare and test the full DMA-direction series rather than copying its final patch alone. The mini's radio PCI IDs and the effect on its Wi-Fi/Bluetooth remain unverified. Gravity's package README does not make Bluetooth a release requirement, whereas our input release goal does.
9. **Audio and power policies need J773g-specific decisions.** Gravity's package spec says J773g speaker protection is in the kernel; its README also refers to a downstream `speakersafetyd` fork. Omarchy's default desktop installs and starts its Asahi speaker daemon. Reconcile the actual kernel, UCM, PipeWire and daemon behavior and verify speaker safety before enabling output. Gravity's M4 research policy disables suspend and hibernate; do not advertise them until tested. HDMI audio and USB audio are separate qualification cases.
10. **A separate kernel package needs boot-tool support.** The draft branch's boot checker explicitly accepts `linux-asahi` and `linux-aurora` and maps them to particular loader names; migration scripts also name Aurora. The M4 candidate currently has no Arch ARM package, matching Mesa package, initramfs/boot chain or recovery entry. Extend the relevant checker, upgrade detection and recovery path for a distinct package name only after defining the matched bundle; preserve a known-good boot.

## Evidence and next gates

The latest Gravity kernel/package and Mesa branch pins were checked with `git ls-remote`; specific newer loader/installer commits were inspected via GitHub. Selected source files from both Aurora heads were fetched at the exact commits above, and the Mesa/kernel UAPI files were compared by SHA-256. The [receipt](2026-10-30-upstream-desktop.json) records the scratch replay and object hashes. The original candidate later completed a local ARM64 Linux full build; see [the build receipt](../kernel-build-2026-10-30.json). It does not include the reconciled R7 scratch changes.

Next: construct a context-bearing, reviewable patch series for the reconciled scheduler/idle/Bluetooth work; add a separate J773g configuration including the required NIC and watchdog options; build and test that complete kernel and matched Mesa/bootloader bundle; then perform controlled physical boot, HDMI and recovery qualification when the mini is available. The [input-device release goal](../INPUT-RELEASE-GOAL.md) remains a separate unimplemented requirement.
